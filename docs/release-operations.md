# Release operations and measured quality — 2026-09-19

This is a verified local release candidate, not an assertion of production deployment. The shared sprint specification remains authoritative. Never substitute a test database backup for an Atlas snapshot.

## Operational contract

- `GET /api/health` remains compatible. `/api/health/live` checks process responsiveness without querying MongoDB. `/api/health/ready` pings MongoDB, returns 200/503 with only `ready`/`not_ready`, and cancels the probe after two seconds. Readiness failures do not attempt to persist an audit event to the unavailable database.
- Responses carry `X-Correlation-ID`, generated by the server and matching Problem Details `traceId` where emitted. Caller-supplied identifiers are not trusted as metric labels.
- .NET meter `BookLibrary.Http`, histogram `booklibrary.http.request.duration` (seconds): route template, HTTP method, numeric response status. Unknown routes use `unmatched`. Handled exceptions preserve the original route template. No raw query, resource ID, token, email or exception text is included.
- Histogram count gives request/error rates by status; 401 on authentication measures failed authentication requests; 409 on loans measures reservation conflicts. Dashboard endpoint duration includes its aggregation work, but is not an isolated database profiler measurement.
- Attach the deployment's metrics collector to this meter. No external monitoring account, exporter, dashboard or alert subscription has been deployed by this change.
- The production auth limiter permits five requests per IP per minute; the sixth returns safe 429 Problem Details. The dedicated test runs the production limiter, separately from the browser host that disables throttling.

## Baseline and provisional budgets

Run `python scripts/measure-local-api.py` against the isolated QA host. It validates the QA marker and never accepts a remote URL. Three warmups plus 30 serial samples per endpoint; all samples must return successful JSON. This is a small seeded loopback baseline, not a load test or production SLO.

Initial regression investigation budgets: paginated reads p95 250 ms and dashboard p95 500 ms on the same local fixture; do not turn noisy workstation measurements into flaky CI assertions.

Initial deployment alert proposals: readiness fails three consecutive 30-second probes; 5xx exceeds 1% over five minutes with at least 100 requests; endpoint p95 exceeds one second for ten minutes with at least 100 observations. Authentication failures and reservation conflicts are investigation signals, not automatic incidents. Recalibrate after collecting real traffic; none of these alerts is claimed to be active.

## Snapshot and recovery rehearsal

`MigrationRehearsalTests` uses a randomly named loopback-only database, serializes exact BSON before migration, checks dry-run counts/non-mutation, applies one transformable document, leaves an anomalous document untouched, verifies a repeated apply changes zero documents, and restores/compares the original BSON. It tests the migration engine and recovery algorithm; it does not test Atlas snapshot service or the production CLI's connection configuration.

Before a real rollout record: environment and approved operator, snapshot identifier/time, successful restore test, migration counts/anomalies, affected IDs, previous/current API and client artifact hashes, and smoke results. API precedes client. Stop on anomalies or reconciliation failure. A rollback selects the previous compatible artifact; database rollback requires a decision about writes since the snapshot, not manual inventory counter changes. If post-snapshot writes exist, reconcile them before restoration. Never use `--snapshot-confirmed` without actual backup evidence.

## CI and repository policy

Backend CI uses locked restore, local replica set and rejects omitted tests. Source checks and pinned Gitleaks scan all fetched Git history with redacted output. The only two exceptions are exact historical fingerprints of illustrative unit-test strings; no broad path/rule exclusion is used.

Frontend browser CI must check out an exact backend revision, run on pull requests and retain evidence. Require `build-and-test` in backend and `test-build-audit` plus `browser` in frontend before merging. As verified through GitHub on 2026-09-19, both `main` branches currently report `protected: false`; adding branch rules requires the repository owner's governance decision. The workflow checks exist, but do not themselves prevent a privileged direct merge.

## Remaining external acceptance

- Owner-approved branch protections and cross-repository merge order.
- Authorized Atlas staging copy, actual snapshot and restoration evidence; production rollout and monitoring collector configuration.
- Human review with a screen reader and actual browser zoom at 200%; keyboard, responsive, CSS magnification and axe automation are supplementary evidence, not a WCAG conformance certificate.
